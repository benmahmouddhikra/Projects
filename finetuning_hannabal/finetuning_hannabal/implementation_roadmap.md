# Hannibal V2 Fine-Tuning Implementation Roadmap

## 1. Delivery objective

Deliver a fine-tuned Hannibal V2 whose Agent 2 produces better-structured, more complete, more natural, and more MENA-adapted contracts while continuing to obtain all law exclusively from RAG indexes.

The source provides:

- Four detailed phases assigned to weeks 1–8.
- A global three-month calendar assigned to weeks 1–12.

The roadmap below preserves both views and marks their timing conflict instead of silently reconciling it.

## 2. Technical baseline

### 2.1 Candidate model and method

- Base model candidates: Llama 3.1 8B or Mistral 7B.
- Alternative: GPT-4o-mini through Azure fine-tuning.
- Recommended fine-tuning method: LoRA.
- Alternative method: QLoRA.
- Full fine-tuning: discouraged.
- Runtime integration target: Agent 2 dynamically loads specialized adapters.

`AMBIGUITY`: The final base model, training method variant, GPU, and cloud provider have not been selected.

## 3. Phase 1 — Preparation, weeks 1–2

| Task | Owner | Source duration | Deliverable |
|---|---|---:|---|
| Take ownership of Agent 2 code | Intern | 2 days | Understanding of the RAG pipeline |
| Identify use cases | Intern + lawyers | 1 day | List of the 50 most frequent contract types |
| Collect corrected contracts | Lawyers | 1 week | 50–100 corrected contracts |
| Clean the data | Intern | 2 days | Dataset in Alpaca format |

### Technical work

1. Trace Agent 2's request-analysis, index-selection, retrieval, clause-selection, generation, validation, and risk-analysis path.
2. Inventory the 50 frequent contract types with lawyers.
3. Collect only corrected target contracts for the initial high-quality corpus.
4. Convert examples into the source-defined Alpaca structure:

```json
{
  "instruction": "Génère un contrat de travail CDI pour un développeur senior en Tunisie, salaire 3000 TND, période d'essai 3 mois.",
  "input": "Parties : E-Tafakna (employeur) et Norchen Mezni (employé). Date de début : 1er juillet 2026. Lieu : Tunis.",
  "output": "# CONTRAT DE TRAVAIL À DURÉE INDÉTERMINÉE\n\n## PARTIES\n...\n\n[CONTRAT COMPLET]"
}
```

5. Reject or flag malformed examples, missing target output, incomplete placeholders, untraceable laws, and truncated vectors.

`AMBIGUITY`: The sources do not define train/validation/test split ratios, duplicate policy, normalization rules, or a canonical placeholder grammar.

## 4. Phase 2 — Dataset construction, weeks 3–4

| Dataset | Transformation | Construction method | Target |
|---|---|---|---:|
| A — Intent → Blueprint | Prompt → contract plan | GPT-4o synthetic generation + corrections | 200 |
| B — Blueprint → Clauses | Plan → clause list | Template extraction + corrections | 300 |
| C — Clause → Drafted version | Clause → legal text | Extract from `accords_index` and `cuad-unified` | 500 |
| D — Contract → Analysis | Contract → omissions/inconsistencies | Generated by Agent 4 | 200 |

Total planned examples across A–D: 1,200.

The general dataset guidance remains:

- 200 examples: minimum/acceptable.
- 500–1,000 examples: recommended/good.
- 2,000+ examples: optimal/excellent.
- One good example is preferred over ten mediocre examples.

### Dataset quality gates

For every record:

- Keep `instruction`, `input`, and `output` semantically separate.
- Preserve contract type, country, language, parties, amounts, duration, and specific information when supplied.
- Ensure the target follows the relevant blueprint order.
- Ensure mandatory sections and clauses are present.
- Preserve placeholders only where the information is genuinely missing.
- Ground legal clauses in the documentary indexes.
- Preserve corrections made by lawyers.

### Source record usage

- Blueprint records supply structure, mandatory/conditional sections, variable points, required elements, and adaptation hints.
- Contract/Q&A records supply complete contract contexts and associated questions and answers.
- Risk records supply detection patterns, risk level, legal basis, recommendation, and impact.
- Legal-clause records supply indexed clause text.

`AMBIGUITY`: The architecture contains no Agent 4. Dataset D's generator must be identified before construction.

`AMBIGUITY`: The global month-one deliverables list Datasets A, B, and C only, although Phase 2 also defines Dataset D.

`AMBIGUITY`: `accords_index`, `cuad-unified`, and the headings in `contrat_example.md` do not establish canonical index names.

| Task | Owner | Source duration | Deliverable |

### Adapter order

1. Hannibal-Employment — priority 1.
2. Hannibal-Commercial — priority 2.
3. Hannibal-SaaS — priority 3.
4. Hannibal-NDA — priority 4.
5. Investment, Real Estate, and Procurement — phase 2 of adapter expansion.

### Evaluation focus

- Required sections.
- Malformed or unreplaced placeholders.
- Clause omissions.
- Internal contradictions.
- Legal hallucinations.
- Drafting quality.
- MENA adaptation.
- Lawyer correction time.
- Generation latency.

`AMBIGUITY`: Phase 3 says to train Commercial, SaaS, and NDA after Employment, but the global month-two deliverable lists only Employment, Commercial, and SaaS.

`AMBIGUITY`: NDA belongs to both the Commercial and NDA adapter categories; adapter routing and evaluation separation are not defined.

## 6. Phase 4 — Integration and validation, weeks 7–8

| Task | Owner | Source duration | Deliverable |
|---|---|---:|---|
| Integrate into Agent 2 | Intern | 2 days | Agent 2 loads adapters dynamically |
| Validate with 50 test contracts | Lawyers | 1 week | Quality score greater than 85% |
| Production A/B deployment | Intern + DevOps | 2 days | 10% of users see fine-tuned version |
| Measure KPIs | Intern | 1 day | Final report |

### Integration behavior

The integrated Agent 2 must retain the source-defined sequence:

```text
analyze request
-> choose indexes
-> retrieve through RAG
-> select clauses
-> generate
-> validate
-> analyze risks
-> send generated contract to Agent 3
```

Adapter loading must not bypass RAG, inject unsupported law, or move legal logic to Agent 3.

`AMBIGUITY`: The exact adapter-selection algorithm, fallback behavior, hot-loading interface, and Agent 2 payload schema are not specified.

## 8. Acceptance gates

| Gate | Target | Measurement |
|---|---:|---|
| Mandatory sections present | 100% in the objective table; greater than 99% in the KPI table | Compare with contract plan |
| Malformed placeholders | 0 | Automatic verification |
| Variables correctly replaced | Greater than 99% | Check `[À COMPLÉTER]` |
| Missing clauses | Less than 2% | Compare with Legal Planner |
| Internal contradictions | Less than 1% | Automated LLM validation |
| Legal hallucinations | 0% | Track reports |
| Drafting similarity/style | Greater than 85% | GPT-4o evaluation |
| MENA adaptation | Greater than 80% | Local-lawyer evaluation |
| Accepted without major change | Greater than 90% | Lawyer feedback |
| Lawyer correction time | Less than 10 minutes per contract | Measured time |
| Generation time | Less than 15 seconds | Application logs |

`AMBIGUITY`: The two required-section thresholds conflict. Both are retained until one is selected.

`AMBIGUITY`: The source does not define the GPT-4o evaluation prompt, legal-style rubric, MENA scoring rubric, baseline sample, test split, or statistical acceptance rule.
